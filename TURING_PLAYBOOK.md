## 1. The job

Handshake AI, Project Turing (site `project-turing-24.learn.joinhandshake.com`, behind a login;
Claude cannot open it). The fellow creates Lean 4 training tasks. One task:

1. Write a prompt (we only do proof-writing tasks: five theorems, exact Lean statements).
2. The platform runs three models on it (each gets an offline Lean environment, up to 6 hours).
3. Check the three outputs. At least one must GENUINELY fail (sorry, missing theorem, build error,
   wrong statement, forbidden axiom). An environment failure does not count. If all three pass,
   the task is rejected: no golden, no rubric.
4. Write our own golden answer: a complete Lake project as a zip, plus a step-by-step explanation
   for the Golden Answer text box.
5. Rubric: 5 to 20 binary criteria, each weight +1, uploaded as a CSV.
6. The platform's judge model grades the outputs and the golden with the rubric.
7. Targets: golden >= 90 percent (we aim at 100), at least one of the 3 outputs < 40 percent.
8. Submit. A reviewer (so far: Alexey) scores it and may send it back with notes.

Pinned environment, never change:
- Lean toolchain `leanprover/lean4:v4.33.0-rc1`
- Mathlib commit `9944fe2973b8dc0b86949101ed98232c07cd54a0`
- In the platform's offline image Mathlib is at `/opt/mathlib4`; models' lakefiles use
  `path = "/opt/mathlib4"`. The platform timer per task is 6 hours.

Claude does the files; the fellow does every platform step (paste prompt, download outputs,
upload golden and CSV, run evaluations, submit) and starts Windows scripts by double-click.

## 2. Working with the fellow (his standing rules)

- Do things yourself and keep his manual steps minimal, but ask him for a manual step whenever it
  saves a long wait (for example: double-click `lean_worker.bat`).
- No long silent waits. Say what is running and hand over each file as soon as it is usable.
- Everything that goes into a submission field (prompt, explanation, rubric CSV, Basic.lean) is
  pure ASCII and generated by a script (a self-checking Python generator), never typed by hand.
- Prompts short, neutral declaration names, no hints about the proof method, no famous names of
  the theorem in the prompt.
- The golden is written only after a genuine failure is confirmed, is our own work, and never
  copies a model output.
- Be brief. Say plainly what is verified (by an official Lean run) and what is not.
- Never promise a model failure or a reviewer score. Aim for a 5/5 review.
- Update the tracker (`TURING_TRACKER_EXPORT.md`) after every step, and append a handoff section
  to `TURING_HANDOFF_2026-10-06.md` when a task reaches a milestone.
- One chat per task.

### 3.1 The Lean worker (all official builds)

The fellow double-clicks `Project Turing\lean_worker.bat` and leaves the window open. It watches
`D:\lean\TuringTask\_jobs\` and refreshes `_jobs\worker_alive.txt` every 5 seconds (read it to
see whether the worker runs). To run a build, create a job folder (commit files from the cloud):

```
D:\lean\TuringTask\_jobs\<job name>\
    src\TuringTask\Basic.lean        and every other file of the project under src\TuringTask\
    src\TuringTask.lean              optional; default is `import TuringTask.Basic`
    check.lean                       optional; run with `lake env lean` after the build
    READY                            empty file - commit it LAST, in a separate commit
```

The worker replaces `D:\lean\TuringTask\TuringTask\` with `src\TuringTask`, runs `lake build`,
then the check file (as `JobCheck.lean`), and writes `log.txt` (while running: `log.tmp`) and a
`DONE` marker. Read `log.txt` by staging it. Job names so far: `001` ... `016c`; use the next
free number with a short tag (for example `017a_t12_statements`).

Rules learned the hard way:
- Never build several Mathlib-importing files in parallel on this laptop (memory error, `failed to
  read file ...olean`). Make the project ONE import chain (A imports Mathlib, B imports A, ...,
  Basic imports the last), or one job per file with a stub `TuringTask.lean`.
- If the build fails, the check part of the log shows STALE results from the previous build.
  Always read the build part first.
- Times: warm worker about 25 s per Mathlib-importing file; the first build after a restart or
  long idle 500 to 730 s. A golden iteration round (whole chain) is 2 to 3 minutes.
- Exit codes 0x40010004 / Ctrl-C in a log mean the window was closed: rerun, it is not a result.
- A model project with a second library needs that folder in `D:\lean\TuringTask` and an extra
  `[[lean_lib]]` in `D:\lean\TuringTask\lakefile.toml`; restore the lakefile afterwards.

### 3.3 Cloud Lean with the laptop's oleans (the fast drafting loop, set up 9 Oct)

`verify_golden_offline.bat` remain the official checks.

One-time on the laptop (done 9 Oct; the chunks are reusable by every later chat): the fellow
double-clicks `Project Turing\pack_oleans_for_cloud.bat` (9 chunks `oleans_01..09.tgz`, the

`D:\lean\_xfer` (manifests `pack_manifest.txt`, `pack_server_manifest.txt`, `pack_ir_manifest.txt`
list the finished chunks with their sizes). Lean needs all three kinds: without `.olean.server`
the import fails with "failed to open file ...olean.server", without `.ir` the interpreter
reports "Could not find native implementation of external declaration".

In every new chat (about 10 minutes):
1. `curl` the toolchain from GitHub and unpack it:
   `https://github.com/leanprover/lean4/releases/download/v4.33.0-rc1/lean-4.33.0-rc1-linux.zip`
   (900 MB; `bin/lean` works directly).
2. Stage the chunks two per call (each under 400 MB, 500 MB per call) and extract each with
   `tar -xzf` into one folder, e.g. `/home/claude/work/pkgs/` (the archives contain paths such as
   `mathlib/.lake/build/lib/lean/Mathlib/...`); delete each archive after extracting (disk
   allowance). Only stage a chunk that is listed in the manifest: a chunk still being written is
   staged incomplete.
3. `export LEAN_PATH=<project>/.lake/build/lib/lean:` followed by the eight
   `pkgs/<pkg>/.lake/build/lib/lean` folders (mathlib, batteries, aesop, Qq, proofwidgets,
   importGraph, LeanSearchClient, plausible), then `lean File.lean` or
   `lean -o <project>/.lake/build/lib/lean/TuringTask/X.olean TuringTask/X.lean` to build an import
   chain file by file (a plain `.olean` is enough for the next file to import it).
4. The first `import Mathlib` takes about 6 minutes (cold disk cache), later ones about 9 s.
   Warnings print as in `lake build`; exit 0 with no output means no warnings.
Keep the Mathlib source checkout for grep (`git fetch --depth 1` of the pinned commit, 150 MB).
A golden of 2,000 lines (task 12) was written and compiled this way in about three hours and
passed the official worker job on the first run.

## 4. Step A - choose a topic (the step that decides everything)

Scoreboard so far (11 tasks):
- No failure, rejected: 1 Smith LCM determinants, 2 circulant determinants, 3 Farey neighbours
  (elementary or linear-algebra glue, 200-620 lines, solved in 12 min to 3 h), 11 Lovasz local
  lemma with five applications (836-1,217 lines, all three solved it), 7.5 Jacobsthal character
  sums for p = 1 mod 4 (1,126-1,781 lines, all three solved it; post-mortem in 4.1).
- Genuine failures: 4 coloured partitions (needs Jacobi's identity; 2 fails), 5 partition theta
  sums (Gauss identities; 1 fail, 1 pass), 6 quadratic Gauss sum sign (1 fail, 1 pass with 2,868
  lines), waris-pc 7 convolution identities (2 fails), 9 cubes mod p / cubic Jacobi sums (1 fail,
  2 pass), 10 Zsigmondy primitive prime divisors (2 fails, the third rollout died).
- Task 12 (Carmichael's primitive divisors for Fibonacci/Lucas numbers): R1 fail (sorry in the
  core), R3 fail (nothing proved), R2 pending; golden 2,017 lines.
- Lesson: choose ONE hard classical core that is missing from Mathlib and that all five theorems
  need, with real downstream work (estimates, exceptions, case analysis). Avoid theorems a model
  can prove without the core, and avoid self-contained finite combinatorics. The best result so far
  (task 10) combined algebra (cyclotomic polynomials), p-adic valuations, real-analytic bounds and
  finitely many exceptional cases.
- Expected golden size for such tasks: 900 to 1,300 lines; budget several hours.

### 4.1 Post-mortem of task 7.5 (Jacobsthal sums): why all three models passed

Not a wording leak: the names were neutral (`csum`, `csum_sq_add_sq`, `card_curve`), no method words,
no mathematician's name. The task was too easy in two structural ways, and both are checkable
before a prompt is compiled.

1. The "missing core" had a short textbook proof. The one lemma that is not in Mathlib (the sum over
   c of chi((u - c)(v - c)) equals -1 for u != v) is a 20-line substitution argument. Everything
   else is finite manipulation inside F_p (x -> t u, the orbits of x -> -x and x -> 1/x, power sums
   sum x^m = 0 or -1, Euler's criterion) plus Mathlib one-liners (`legendreSym.eq_pow`,
   `quadraticChar_card_sqrts`, `quadraticChar_sum_zero`, `ZMod.exists_sq_eq_neg_one_iff`). The whole
   route is one chapter of Berndt-Evans-Williams / Ireland-Rosen; the models reproduced it in
   1,100 to 1,800 lines, which is well inside their 6-hour budget (task 6 R3 wrote 2,868 lines;
   task 11: 836 to 1,217). Length never fails them; only a missing idea does.
2. The five statements formed a ladder that spelled out the proof. Theorem 1 (S(c)^2 + S(r)^2 = 4p)
   and theorem 3 (S(1) mod 8) ARE the textbook lemmas for theorem 2 (S(c)^2 = 4a^2); theorems 2 and
   3 pin the sign needed for theorems 4 and 5; theorem 5 is theorem 1's sum plus one Mathlib lemma.
   Writing the intermediate lemmas as theorems hands the model the plan and the order. Compare task
   10 (two failures): the five theorems were one hard statement and four consequences, and the real
   work (cyclotomic values, valuations, size bounds, exceptional cases) appeared in none of them.

Hardness checklist - apply to every new topic BEFORE writing the generator; reject if two or more
answers are "yes":
- Short-core test: can the part that is missing from Mathlib be proved in under about two textbook
  pages of finite computation (substitutions, orbit counting, power sums, ring identities)?
- Ladder test: is some theorem k a lemma used in the standard proof of another theorem j? If yes,
  the prompt scaffolds the proof. Prefer one hidden hard core and five consequences that do not
  prove each other; or put the core as the single hardest theorem and make the others corollaries
  that need it but do not reveal how to prove it.
- Textbook test: is the complete route a single named chapter or exercise (Ireland-Rosen, Hardy-Wright,
  Berndt-Evans-Williams, Apostol)? Then the model has it memorised; difficulty is only lines.
- Mathlib-assist test: list the Mathlib results the standard route uses (Euler's criterion, card of
  square roots, character sum zero, two squares, quadratic reciprocity, Jacobi sums, cyclotomic
  evaluations, resultants). If with these the new work is under about 300 lines, too easy.
- Finite-manipulation test: can everything be done inside one finite ring (F_p, Fin n, Finset) without
  real or complex estimates, algebraic integers, generating functions or an inductive size argument?
  All five full passes so far (tasks 1, 2, 3, 7.5, 11) were of this kind.
- What produced failures: an identity or theory whose proof needs a non-obvious idea AND a mix of
  areas: q-series identity via Gaussian binomials (task 4, 2 fails), sign of the Gauss sum via sines
  or a DFT (task 6, 1 fail), theta-type convolutions (waris-pc 7, 2 fails), cubic Jacobi sums in
  Z[omega] (task 9, 1 fail; Mathlib's Jacobi-sum API made it easier), Zsigmondy with cyclotomic
  algebra + valuations + real bounds + exceptions (task 10, 2 fails).
- Calibration numbers to collect from the platform for every task: the run time of each model
  (minutes) and the line count of each output; record them in the tracker row. A pass under 2 hours
  means the topic was far too easy; a pass near 6 hours means the topic was borderline.

Prompt design rules that worked:
- Five theorems, NO definitions (rubric = 1 build item + 5 proof items = 6; an output that only
  builds scores 1/6 = 17 percent, one proved theorem 2/6 = 33 percent). With one definition the
  numbers become 2/7 = 29 and 3/7 = 43 (too high) - prefer no definitions, never more than one.
- State everything with Mathlib objects (`Nat.Prime`, `Nat.divisors`, `ZMod p`, `Finset.card`,
  `Real.exp`, `Complex.exp`, `legendreSym`, ...), in ASCII Lean syntax: `Nat`, `Int`, `Real`,
  `->`, `<=`, `/\`, `\/`, `forall`, `exists`, `Not`, `fun x => ...`, `Finset.sum`, explicit casts.
- Neutral names (`exists_prime_sub`, `card_cubic`), no names of mathematicians, no method words.
- The task must test mathematics, not recall of one obscure Mathlib name (API-neutrality check).
- Check the mathematics numerically in the generator with exact arithmetic where possible, and
  check that each hypothesis cannot be dropped (counterexamples without it).

Novelty check (before writing files; record results in the tracker):
- Mathlib at the pinned commit (grep the shallow checkout for key words and the statements).
- Benchmarks: PutnamBench, miniF2F, ProofNet, compfiles, google-deepmind/formal-conjectures.
- Public repos that grow daily: `TauCetiProject/TauCeti` (12,000+ AI-written files),
  `tomdif/RamanujanLean` (q-series, theta functions, sums of two and four squares - this whole
  family is OFF LIMITS), `AxiomMath/RogersRamanujan` (Jacobi triple product),
  `riccardobrasca/KummerCriterion` (Kummer congruences, Voronoi, quadratic Gauss sum sign,
  h^-, L-values - Bernoulli congruences are OFF LIMITS), `leanprover-community/flt-regular`,
  and for analytic number theory `AlexKontorovich/PrimeNumberTheoremAnd`.
- Web search "<topic> Lean 4 formalization" and Isabelle AFP (disclose AFP matches).
- Already in Mathlib (do not use): von Staudt-Clausen, Jacobi sums with J = -1 + z(mu-1)^2,
  degrees of factors of cyclotomic polynomials mod p, Burnside, Dirichlet's theorem on primes in

## 5. Step B - the prompt (generator + official compile)

Folder `tasks\task N\`. Copy `tasks\task 10\turing_t10_generator.py` to
`turing_tN_generator.py` and change only the task part (TASK, COUNT_WORD, KEEP, PRELUDE,
THEOREMS, DEF_CHECK, PROMPT_BODY, self_check). The shared part writes:
- `taskN_prompt.txt` (the text to paste; pure ASCII; math in `$...$`),
- `TuringTask\Basic.lean` (statements with `sorry`),
- `StatementAndAxiomsCheck.lean` (one `example` per theorem that type-checks only if the submitted
  theorem has exactly the prompt's statement, then `#print axioms` for each),
- `check_outputs.bat` (old one-click checker, superseded by the worker).
Use `_explicit_args` (top-level binders only) for the check file; an old regex bug picked up
`(p : Int)` inside binder types.

Prompt shape (task 10 is the model):
1. "Create a Lean 4 project and prove the five theorems below in `TuringTask/Basic.lean`. This is a
   proof-writing task."
2. "Mathematical statement." Numbered statements in plain English with `$...$` math.
3. "Lean statement." One sentence on conventions, then the full file in a ```lean block:
   `import Mathlib`, `namespace TuringTask`, the five theorems each `:= by\n  sorry`,
   `end TuringTask`. Lines at most 100 characters.
4. The Rules paragraph, verbatim:
   "Rules. Helper definitions and lemmas are allowed, in this file or in other project files that it
   imports, and so is any kernel-checkable proof strategy. Keep `import Mathlib`, the namespace
   `TuringTask`, and the names and statements of the five theorems unchanged. Do not use `sorry`,
   `admit`, `native_decide`, new axioms, or any other way around the kernel: for each of the five
   theorems `#print axioms` must report only `propext`, `Classical.choice` and `Quot.sound`.
   Environment: Lean toolchain `leanprover/lean4:v4.33.0-rc1`, Mathlib commit
   `9944fe2973b8dc0b86949101ed98232c07cd54a0`. Verify with `lake build`; it must finish with no
   errors."
This covers the site's list: problem, task type, file, declaration names, imports, helper policy,
banned escapes, versions, check command.

Official compile before handing over: worker job `0NN_tN_statements` with `src\TuringTask\Basic.lean`
= the generated file and `check.lean` = `StatementAndAxiomsCheck.lean`. Expected: `Build completed
successfully`, exactly five `declaration uses sorry` warnings, check exit 0 (axiom lists show
`sorryAx`, as expected for a skeleton). Then save the log as `tasks\task N\statements_worker_log.txt`,
give the prompt to the fellow, update the tracker.

## 6. Step C - check the three model outputs

The fellow puts the outputs (zips) in `tasks\task N\model_outputs\` (sometimes a sub-folder `r3\`
with several zips: intermediate attempts plus the final project; use the final project and say
which one you used). A rollout that shows "Rollout failed" has no output; do not ask him to retry
if a genuine failure already exists (a retry can take 6 hours).

For each output:
1. Stage and unpack in the cloud. List files, find the project root and `TuringTask/Basic.lean`.
2. Compare the five statements with the prompt (whitespace-insensitive). Grep all Lean files for
   `sorry`, `admit`, `native_decide`, `axiom`, `unsafe`, `implemented_by`, `extern`, `opaque`,
   `set_option`, `instance`, `attribute`, `notation`, `macro`, `elab`, `debug.skipKernelTC`.
3. Official run: worker job `0NN_tN_rK` with the output's `TuringTask\` folder as `src\TuringTask\`,
   its `TuringTask.lean`, and `check.lean` = our `StatementAndAxiomsCheck.lean`. One job at a time.
4. Read the log: build exit code; `declaration uses sorry` warnings; axiom lists (`sorryAx` = fail);
   `Unknown identifier` in the check (theorem absent = fail); type mismatch in an `example`
   (statement changed = fail).
5. Record a short factual failure statement, for example: "Build exit 0, but `exists_prime_sub`
   ends in `sorry` at line 1757; all five theorems depend on `sorryAx`." or "The project builds,
   but `TuringTask/Basic.lean` contains none of the five theorems; the check file reports Unknown
   identifier for all five."
6. Environment failures (missing Mathlib, download errors, olean read errors on our laptop) do not
   count: rerun. A README that claims success means nothing; Lean decides.
7. Read only what the check needs. Do not read the proof bodies of passing outputs: the golden must
   be independent. Grepping for forbidden words is fine.
If no output genuinely fails: the task is rejected. Tell the fellow plainly, update the tracker,
write no golden.

## 7. Step D - the golden answer

Plan the mathematics first (write the plan into the handoff before coding if it is long). Then:

Development loop (through the worker, about 2 to 3 minutes per round):
- Develop in the cloud as text, send the whole chain as one job (`0NN_tN_golden`, then `b`, `c`,
  ...), read every error, fix, repeat. A single big file during early development shows all
  errors in one round; split into an import chain of 5 to 7 files (each under about 400 lines)
  for the final version.
- Final file layout (task 10): `TuringTask/Hcyc.lean` (imports Mathlib) -> `Prim` -> `Size` ->
  `Zsig` -> `Apps` -> `Main.lean` (the five theorems with their own names, e.g. `primitive_sub`)
  -> `Basic.lean`. `TuringTask.lean` = `import TuringTask.Basic`.
- `Basic.lean` = the prompt's Lean block EXACTLY (pure ASCII), plus `import TuringTask.Main` after
  `import Mathlib`, with each `sorry` replaced by one line `exact <name in Main> <args>`.
- Every source file starts with `import Mathlib` or an import of the previous file (the chain).
- Final build must have NO warnings (the linters flag unused variables, unused `have`, `<;>`
  where `;` would do, no-op tactics, deprecated tactics). No `sorry`, `admit`, `native_decide`,
  `axiom`, `set_option`, `instance`, `unsafe`, `implemented_by`, `extern`, `opaque`.
- Lines at most 100 characters.
- Own names, own structure. Before finishing, scan the golden against every model output for
  shared declaration names and shared long lines; only the prompt's statement lines may coincide.

Lean gotchas at the pinned versions:
- `push_neg` is deprecated: use `push Not`. `Nat.dvd_sub'` is gone: use `Nat.dvd_sub`.
- A doc comment must come AFTER `omit [...] in`, not before. Unused section variables: use
  `omit [Fact p.Prime] in` before the lemma.
- `AlgHom.mem_range` must be applied as `(AlgHom.mem_range _).mp`.
- `set x := Complex.exp ...` with big expressions can time out in whnf: introduce the value with
  `obtain` from an existential `exists x, x = ...` (proved by `rfl`) and rewrite with the equation.
- `rw [<- lemma]` (that is, the left arrow) whose right side is `1` rewrites every `1` in the goal.
- `positivity` does not use hypotheses (casts of variables known positive only from hypotheses).
- `induction` keeps hypotheses that mention the variable: `clear` them first if rcases fails later.
- With `open Finset`, `mem_antidiagonal` is ambiguous: use full names.
- With all of Mathlib imported, a `def` using `Finset.Icc` on `Int` must be `noncomputable`.
- `Sym2.mk` takes two arguments at this commit.
- Explicit lambdas passed to lemmas leave beta-redexes; `.trans` with `exact` handles them.
- `goldenRatio`/`goldenConj` (notation `phi`, `psi` under `open Real goldenRatio`) are `abbrev`s that
  `ring` unfolds; prove polynomial identities in them as generic lemmas in variables `a b` with the
  needed relation as a hypothesis, or by `linear_combination c * goldenRatio_sq` with the exact
  cofactor `c` (compute it with sympy's polynomial division).
- `set x := ... with hx` leaves `x` transparent to `rw` (it may rewrite inside the value); for an
  opaque name use `generalize` or state an auxiliary lemma over a variable.
- `padicValNat.pow a n : padicValNat p (a ^ n) = n * padicValNat p a` takes the base and the
  exponent; `padicValNat.mul` needs the two nonzero proofs; `padicValNat_dvd_iff_le (ha : a /= 0) :
  p ^ n | a <-> n <= padicValNat p a`; `padicValRat.mul/zpow/of_nat`; `padicValRat_def` gives
  `padicValInt p q.num - padicValNat p q.den`.
- `Nat.exists_eq_pow_mul_and_not_dvd (hn : n /= 0) (p) (hp : p /= 1)` destructs as
  `<k, m, hpm, rfl>` (non-divisibility first, then `n = p ^ k * m`).
- `Finset.card_filter_add_card_filter_not`, `Finset.card_le_card_of_injOn`, `Nat.sum_divisorsAntidiagonal'`
  (`f (n / i) i` form), `ArithmeticFunction.sum_eq_iff_sum_mul_moebius_eq` and
  `prod_eq_iff_prod_pow_moebius_eq_of_nonzero` (both over `n.divisorsAntidiagonal` with
  `mu x.fst` and `x.snd`), `Nat.totient_mul_of_prime_of_dvd`, `Polynomial.expand_eval`,
  `cyclotomic_eq_prod_X_sub_primitiveRoots` with `Complex.isPrimitiveRoot_exp` and
  `IsPrimitiveRoot.norm'_eq_one`, `Complex.card_primitiveRoots`, `Polynomial.eval2_at_apply` with
  `map_cyclotomic` to move a real cyclotomic value to `C`.
- `decide` fails with "Expected type must not contain free variables" when a `Fact` instance is in
  scope: use `decide +revert`. `split_ifs` splits nested `if`s too; to keep an inner `if` intact use
  `by_cases h` and `rw [if_pos h]`. `rw [h] at hA; push_cast at hA` for a `Nat.cast_sub`.
